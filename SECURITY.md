# Security boundary

BREACH//5 contains an intentionally vulnerable, shell-backed educational engine. It is not a general-purpose sandbox and must not be exposed directly to the internet.

## Public surface

Only the `game` coordinator is published by Compose. The vulnerable and patched gateways and both workers are attached only to internal Docker networks.

The public API accepts enumerated card IDs. It does not accept arbitrary raw request-targets, commands, cookies, or free-form player names. The coordinator converts a valid team selection into one of the server-owned requests.

## Containment

All services run as the unprivileged `node` user with:

- read-only root filesystems
- all Linux capabilities dropped
- `no-new-privileges`
- PID, CPU, memory, file-descriptor, and file-size limits
- small `noexec,nosuid,nodev` worker tmpfs mounts
- no host mounts
- no Docker socket
- no host network
- no external network on engine backplanes

These controls reduce risk but do not make an intentionally vulnerable shell sink safe for direct public exposure.

## Secrets and participant data

- `.runtime/booth.env` is generated locally and ignored by Git.
- proof and engine tokens are not returned by public APIs.
- application logs do not log request bodies, bearer tokens, IP addresses, or User-Agent strings.
- anonymous callsigns are generated by the server.
- each browser generates a random device ID and stores it in `localStorage`; the bearer participant token is stored in `sessionStorage`.
- session state is in memory and expires after approximately 15 minutes.

The device ID exists only to reconnect refreshes and duplicate tabs to the same anonymous participant. It is client-controlled, is not an authentication factor, and must not be treated as a durable or unique person identifier. Clearing site data or using another browser profile creates another ID.

Reverse proxies, CDNs, Docker, and hosting providers can maintain their own access logs. Their configuration must be audited before claiming that IP addresses are not collected.

## Capacity and abuse boundary

The coordinator applies a short join-rate limit and a maximum player count per round. These controls are operational safeguards, not a Sybil defense. A participant who repeatedly changes the client-generated device ID can still consume slots in the current and queued rounds on a shared instance.

For a booth deployment:

- limit access to the reviewed participant network or a reviewed HTTPS ingress;
- apply connection and request-rate limits at the ingress, independently of the application limit;
- monitor current and next-round counts on the large screen;
- keep an operator able to restart the scoped Compose project if the lobby is intentionally exhausted;
- do not claim abuse resistance without testing the actual AP, reverse proxy, and event-network policy.

## Deployment

The default published address is loopback-only. `PUBLIC_BASE_URL` is the canonical participant address used by both the QR and the large-screen text; it must be reachable from the participant device and must not point to loopback for a multi-device event. For a booth deployment, place the coordinator behind a reviewed HTTPS ingress or use a separately reviewed event network. Do not publish the engine networks or add a host/Docker socket mount.

`npm run down` removes only the named operating Compose project. Every `npm run verify` invocation uses its own random Compose project and image, atomically installed environment manifest, verification-only loopback proxy, and Docker-assigned random backend port, so concurrent runs do not share mutable state. A child heartbeat keeps an active manifest fresh even while the parent is blocked in a Docker build. Each run attempts scoped cleanup on success and failure; a later run immediately recovers a manifest whose owner PID has exited, or waits for a stale heartbeat before recovering a possible PID-reuse case. Recovery always uses the exact trusted project marker and never performs a broad Docker prune.

Compose interpolation values used by the operator CLI come from the selected runtime environment file. Ambient `ENGINE_TOKEN`, `BREACH5_BIND`, `BREACH5_PORT`, `PUBLIC_BASE_URL`, and related Compose override variables are removed before invoking Compose so they cannot silently change the audited deployment or secret set.

## Reporting

Do not include runtime proof values or bearer tokens in a public issue. Provide a minimal reproduction that identifies the affected route and expected/observed behavior.
